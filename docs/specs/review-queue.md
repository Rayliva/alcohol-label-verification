# Spec: password gate and agent review queue

Status: **implemented and deployed.** Updated 2026-08-11 to match what ships.

Traces to `requirements.md` (Sarah Chen: "An agent pulls up an application, looks
at the label artwork, and checks that what's on the label matches what's in the
application") and to the decision record in this file's Open questions.

## Why this exists

The shipped flow is upload-first: the agent supplies both the artwork *and* the
declared field values by hand. That inverts the brief. Sarah's complaint is that
agents "spend half their day doing what's essentially data entry verification" —
and the current screen opens by asking them to do data entry. The application
already exists in the agent's world; they pull it up, they do not key it in.

This spec makes the queue the front door and keeps upload as a secondary action.

## Boundaries — what this does NOT do

- **No applicant role and no second persona.** One role: agent. The brief has no
  applicant user, and inventing one to justify a portal is scope this cannot
  defend.
- **No database.** The queue is in memory, seeded at startup, and lost on
  restart. C-2 stands: nothing is persisted.
- **No user accounts, no credential store, no password reset.** A single shared
  username and password read from the environment. No bcrypt question, because
  there is no stored credential to hash.
- **No COLA integration.** The seeded applications are mock data.
- **No change to the rule engine, verdict names, or the pipeline.** `PASS` /
  `NEEDS_REVIEW` / `FAIL` stay exactly as they are.

## Behaviour

### 1. Password gate

- One username and one password, from `AGENT_USERNAME` / `AGENT_PASSWORD` in the
  environment (`.claude/rules/secrets.md`). `.env.example` ships both blank.
- Startup asserts both are set. A missing credential fails loudly at boot rather
  than silently serving an open app (`.claude/rules/error-handling.md` 3).
- Successful sign-in sets a signed, HttpOnly session cookie. Every API route
  except `/health` requires it; an unauthenticated call returns a typed 401,
  never a bare one.
- Sign-in is compared in constant time.
- **The credential is never displayed.** Not on the login page, not in the
  README, not in any tracked file. It is delivered out of band.
- This is a demonstration gate, not a security control, and the README says so.

### 2. Seeded queue

- At startup the app loads a fixed set of sample applications: label image,
  declared field values, beverage type, and an already-computed result.
- Results ship pre-computed rather than being analysed at boot — the queue is
  populated instantly, needs no Anthropic key, and is identical on every run.
  They are generated by the real pipeline via a checked-in script, not written
  by hand.
- The seed set deliberately spans all three outcomes, including at least one
  `NEEDS_REVIEW` case matching Dave Morrison's STONE'S THROW example and one
  warning-statement `FAIL`.

### 3. Queue screen — the landing screen after sign-in

- A table, one row per application: brand, beverage type, verdict chip, and the
  decision, if one has been made.

  **No timing column.** These verdicts were recorded at build time rather than
  computed when the row was opened, so a stopwatch beside them reports the
  machine that made the recording. The five-second budget is demonstrated where
  it is actually spent, on the upload screen.
- **Default sort surfaces `NEEDS_REVIEW` first** — the rows needing human
  judgment are the ones an agent is uniquely needed for.
- Verdict is carried by icon *and* text *and* colour, never colour alone
  (`.claude/rules/accessibility.md` 5).
- A "+ Submit new application" action in the masthead leads to the existing
  upload flow. It sits in the chrome rather than in the queue because it is
  reachable from every screen, and it is the page's one dominant action.

### 4. Detail screen

- Reuses the existing `ResultsScreen`: label image with evidence crops, declared
  versus observed side by side, per-field verdict, warning statement called out
  separately.
- Adds a decision control, approve or reject, with one optional note that is
  saved with whichever is pressed. `override` is still what the API records
  when a flagged label is approved, but it is inferred from the verdict rather
  than offered as a third button an agent has to choose between.
  Decisions live in the same in-memory store as batch jobs and are lost on
  restart; the UI states this rather than implying durability.
- Back to the queue returns to the same sort position.

### 5. Upload stays synchronous

- Single-label upload keeps its current behaviour: the request blocks, the agent
  watches it complete, and the elapsed time is displayed. This is the live
  demonstration of the 5-second budget and must not become a background job.
- A completed upload is added to the queue for the session.
- Batch upload is unchanged: async, pre-flight validated, determinate progress.

## Acceptance criteria

1. Given no session cookie, when any API route other than `/health` is called,
   then a typed 401 is returned and no verification work runs.
2. Given `AGENT_PASSWORD` is unset, when the app boots, then it fails with a
   message naming the missing variable.
3. Given valid credentials, when the agent signs in, then the queue screen is
   the first thing rendered.
4. Given the seeded queue, when it first renders, then every `NEEDS_REVIEW` row
   sorts above every `PASS` and `FAIL` row.
5. Given the seeded queue, when the app starts with no `ANTHROPIC_API_KEY` and
   no Cloud Vision credential, then every seeded row still shows its verdict,
   because nothing about it is recomputed.
6. Given a label uploaded through "+ Submit new application", when it completes,
   then the elapsed time is shown on screen and the row joins the queue. That
   elapsed time is shown for uploads only, never for a seeded row.
7. Given a restart, when the agent signs in again, then the queue is back to its
   seeded state and any decisions made earlier are gone.
8. Every control is reachable by Tab, activatable by Enter or Space, and
   queryable by `getByRole(role, { name })`.

## Documentation this invalidates

Landing this change makes three published statements false. They change in the
same commit:

- `README.md:327` — "Authentication | Not requested…". Becomes a justified
  demonstration gate, with the reasoning written out.
- `README.md:328` — the persistence row needs the queue's restart behaviour
  added; "nothing is stored" stays true and gains a sentence.
- `docs/PRD.md` out-of-scope rows 1 and 4 — auth and multi-user. Row 4 stays
  excluded (still one role); row 1 is now a scoped inclusion.

## Open questions

1. **Seed size.** Eight to twelve rows is enough to make a queue read as a queue
   without turning the landing screen into a wall. Confirm.
2. **Pre-computed seed results.** They come from the real pipeline and are
   regenerable, but they are fixtures rather than live analysis. The README must
   say so plainly. Confirm this is the right trade against a slower, key-
   dependent boot that analyses the seed set live.
3. **Decision persistence.** Approve/reject/override vanish on restart. Accepted
   as a prototype constraint, or is a session-scoped banner enough to set the
   expectation?
